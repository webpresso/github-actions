# setup-wp account sign-in for login-only wp

## Product wedge anchor

- **Stage outcome:** Consumer CI can move to the login-only wp 0.0.23 with no stored secret
- **Consuming surface:** setup-wp action inputs and the workflow_call contract of the four reusable workflows
- **New user-visible capability:** GitHub OIDC sign-in for wp inside Actions jobs, a masked break-glass entitlement input, and a caller-selected wp version on every reusable workflow

## Summary

The user decided on 2026-11-17 that the wp CLI and Webpresso Desktop are login-only, with one login-only release, product version 0.0.23 (0.0.22 shipped ungated). The user also approved amending VISION ('local-first / no account') and ADR 0004 for sign-in; neither lives in this repository, so the amendment is recorded in docs/research/2026-11-17-setup-wp-login-only.md as the authority for this lane. From 0.0.23, every non-exempt wp command exits 77 unless a verified entitlement exists. Consumer CI installs wp only through this repository: the setup-wp composite action and the reusable workflows changesets-release, cloudflare-preview, cloudflare-production and webpresso-security. This blueprint makes them able to sign wp in without a stored secret, while every caller on an older version keeps working.

Revision 2 (2026-11-17, after an implementation review of the round-1 head): the round-1 plan put the CI entitlement under a setup-wp-chosen WEBPRESSO_HOME (RUNNER_TEMP/webpresso-home). The app lane's login-only plan (webpresso/app blueprint login-only-apps, decision D7 and auth-dir.ts) resolves the auth directory to RUNNER_TEMP/webpresso/auth whenever GITHUB_ACTIONS is true and RUNNER_TEMP is set, whatever WEBPRESSO_HOME says, and its `wp auth status --json` shape carries no path. With the real wp the round-1 step would have skipped its own masking silently, never checked where the entitlement landed, and moved every other piece of wp state into an empty home. This revision adopts the app lane's path as the one contract, stops touching WEBPRESSO_HOME, fails closed when the entitlement is not where that contract puts it, captures wp's sign-in output until the entitlement is masked, turns a break-glass entitlement below the floor into a warning (so a pre-floor caller forwarding the secret keeps working), warns when break-glass is used, and records the review's documentation findings for both waves. Revision 3 (2026-11-18) replaces the planned deletion of the root package.json with a minimal private workspace marker, because deleting it was measured to break `wp format`, which the promotion row and the preflight format stage run.

Wave 1 (PR A, merged commit S) changes setup-wp only. A second composite step signs wp in after the install step. New input `auth` (auto, oidc or none; default auto) and new secret-valued input `entitlement` (break-glass only, default empty). The login-only floor 0.0.23 is one constant in that step; the comparison uses the numeric major.minor.patch core, so a 0.0.23 prerelease counts as login-only. auto signs in when the version is at or above the floor and is a no-op below it; oidc requires the floor; none never signs in and warns when the version is at or above the floor. An entitlement given below the floor in auto mode is ignored with a warning and wp is never invoked; with auth none, or with oidc below the floor, it fails with exit 20. When sign-in is required and neither ACTIONS_ID_TOKEN_REQUEST_URL nor an entitlement is present, the step fails before any network call and names the fix: `permissions: id-token: write` (fork pull requests receive no id-token). An entitlement is masked with ::add-mask:: before any other output, passed through the step env to `wp auth import --stdin` (never argv, never GITHUB_ENV), and takes precedence over OIDC, because break-glass exists for the case where api.webpresso.ai cannot exchange; a break-glass sign-in ends with a ::warning:: naming kind breakglass and the expiry. Otherwise the step runs `wp auth ci`, which owns the OIDC request (audience https://api.webpresso.ai), the masking of the ID token and the exchange. The CI entitlement lives in wp's own Actions auth directory, ${RUNNER_TEMP}/webpresso/auth (one constant in the step, matching the app lane's D7), which the runner deletes after the job, so it never lands in $HOME, a cache, an artifact or a persistent runner's disk. setup-wp neither sets nor exports WEBPRESSO_HOME. Before invoking wp the step refuses with exit 21 when RUNNER_TEMP is unset or not a directory, when ${RUNNER_TEMP}/webpresso or its auth child already exists as anything other than a real directory, or when an entitlement.jwt already exists there as a symlink or any other non-regular file (a planted link could redirect the entitlement write out of RUNNER_TEMP before any later check). The output of `wp auth ci` or `wp auth import` is captured in a mode-0600 file under RUNNER_TEMP; the step then masks the entitlement file and only afterwards prints the captured output. After sign-in the step requires ${RUNNER_TEMP}/webpresso/auth/entitlement.jwt to be a regular file, not a symlink, whose physical directory lies inside RUNNER_TEMP, else it fails with exit 19 naming the path, so any drift between this action and wp fails loudly at the first login-only run instead of silently skipping the masking. It then requires `wp auth status --json` to report state signed-in with kind ci or breakglass (exit 19 otherwise). The step invokes the installed binary by its WP_INSTALL_DIR path, not by PATH lookup. Tool-cache hits become verified: the expected digest is the caller `checksum` when set, else a `wp.sha256` record that setup-wp seeds next to the cached binary from the verified archive. A hit with no expected digest is treated as a miss and downloaded; a mismatch fails with exit 16. The checksum input stays the only independent trust root, because anything able to write the tool cache can rewrite both files. A self-test job runs the in-repo action against the published 0.0.21 with auth auto and no id-token, proving the skip path for real. The README states honestly that callers below the floor run unchanged only on releases that publish install archives (0.0.16 or later; 0.0.6, 0.0.9, 0.0.10 and 0.0.13 publish flat binaries and exit 6 at this revision, a break that predates this blueprint), that the `entitlement` input is masked before any output only when it comes from `secrets.*` (the runner prints a composite step's env), and how Dependabot and fork pull requests behave (exit 17; skip wp-dependent jobs for them or accept the failure). The stray npm-init package.json from #57 (a test script that always fails and a missing main index.js) is replaced in its own commit by a two-field private workspace marker, name and private: true, with no scripts or dependencies; deleting it outright makes `wp format` refuse the checkout with 'Package not found in workspace'. The README and self-test.yml stop claiming 'no package.json' and say what the file is for.

Wave 2 (PR B, merged commit W) repins the four reusable workflows from setup-wp@2003ca95 to S. Each workflow gains an optional `wp_version` input forwarded verbatim to setup-wp `version`, so W can land before 0.0.23 exists and consumers choose the login-only version by input; this breaks the R8/R10b circular pin of the program. Each also gains an optional `wp_entitlement` workflow_call secret, forwarded only to setup-wp `entitlement`. The default cannot stay 0.0.6: S installs only releases that publish the archive contract, and the dated asset listing in the research note shows 0.0.6 and 0.0.13 publish none. The default is 0.0.21, the release the self-test live job proves; 0.0.22 (Latest since 2026-11-17T20:22Z) behaves identically below the floor and is scheduled for deletion with 0.0.21. `id-token: write` is added to the changesets-release and webpresso-security jobs (both run wp; preview and production already grant it). A caller moving its pin to W must grant id-token: write on those calls, or GitHub refuses the run at startup. That is the one caller-visible change at the new pin; the README states it as a migration step, together with the scope of the grant: every later step of the job can mint OIDC tokens for any audience and read the entitlement, so id-token stays off every job that does not run wp. PR #60 is superseded: its wp_version idea is carried here with an installable default; its formatter, tsconfig, guardrail and test-rename work is not. Only its .oxfmtrc.json and .gitignore are reused verbatim in the plan commit, because `wp format --check` is the only admitted promotion row this Bun-native repository can execute.

Out of scope: refusing versions below the floor or non-default release-repo mirrors (the distribution-removal lane, after consumers are repinned); the wp CLI verbs themselves (webpresso/app); OIDC trust bindings and the exchange endpoint (monorepo); consumer repins. Handoffs: (1) the removal lane moves the wp_version default and the self-test live job to 0.0.23 before v0.0.21 and v0.0.22 are deleted; (2) the consumer repin lane moves the version with the pin in every consumer file, because aksaprocess.tr (ci, harness-gate, architecture-drift, security-scan, deploy-preview at 0.0.9) and framework (ci, quality, release at 0.0.10) pin versions that publish no install archive; (3) the app lane keeps the Actions auth directory at RUNNER_TEMP/webpresso/auth and the entitlement file name entitlement.jwt, or changes the one constant in setup-wp in the same release window; (4) the monorepo lane decides whether the exchange also binds job_workflow_ref, knowing that direct setup-wp callers run in their own workflows.
